# 用語集

サービスで使う言葉と、コードでの名前をそろえるための表。まだドラフトで、[vision.md](vision.md) に書いてある語のほかは決まっていない。コードでの名前は、どの語もまだ決めていない。

## vision.md にある語

| 用語 | 意味 |
| --- | --- |
| 投稿 | 撮って残すもの。流れて消えず、後から価値が増えていく |
| 認識 | 撮ったものを AI が読み取ること |
| 注釈 | 認識の上に人が重ねるもの。注釈で次の認識が賢くなる |
| 本人 | 投稿した人。投稿が誰かの役に立ったときに知らせる相手 |
| カテゴリ | 最初に扱うカテゴリはまだ決めていない。撮る対象の種類という意味で使っているが、これも案 |
| 切り口 | 投稿をどんな括りで集めるか。「今日の〜」や「人生で一番の〜」がありうる。まだ決めていない |

## 案の段階の語

企画の段階で使っていた語。意味も名前も決まっていない。

| 用語 | コードでの名前の案 | 意味 |
| --- | --- | --- |
| 特徴 | 下の論点 2 | カテゴリごとに決まった項目（名前、作り手、産地など）と、その値 |
| カテゴリ定義 | `CategoryDefinition` | カテゴリごとの特徴の一覧。コードでなくデータとして持ち、カテゴリを足してもコードを変えない |
| 出どころ | `Source` | 特徴の値を何が埋めたか（写真の文字、AI の推測、辞書、人） |
| 人の関わり | `HumanAction` | 人が値にどう関わったか（そのまま保存した、候補から選んだ、直した、わからないと答えた） |
| 確認 | `Confirmation` | ほかの人が値を正しいと認めること。特徴ごとに数える |
| 辞書 | 下の論点 3 | バーコードなどをキーにして、みんなで育てる対象ごとの情報 |
| 感想 | 下の論点 4 | 投稿した人の主観。初期設定では自分だけに見える |
| お題 | 下の論点 5 | 世界中の人が同じ日に撮る対象 |
| 写真 | `Photo` | 投稿に付く画像。1 回の投稿に複数枚ありうる |
| 画像ベクトル | `ImageEmbedding` | 写真から作る見た目の特徴量。似た投稿を探すのに使う。写真から作り直せる |

## 決めてほしいこと

### 1. 投稿をコードで何と呼ぶか

企画の段階では、同じものを「記録」や `Observation` とも呼んでいた。`Observation` は Swift の Observation モジュール（`@Observable`）や、Vision の `RecognizedTextObservation` などの型と紛れる。

- 案 A: 日本語は「投稿」、コードは `Post` にそろえ、「記録」は使わない
- 案 B: 公開する行為を「投稿」、積み上がるデータを「記録」（`Record`）と分ける

### 2. 特徴をコードで何と呼ぶか

Swift Testing に `Trait` プロトコルがあるので、単体の `Trait` は型名に使えない。

- 案 A: 日本語は「特徴」のまま、コードは `TraitValue`・`TraitDefinition` のように後ろに語を付ける
- 案 B: 日本語を「属性」に変え、コードは `Attribute` にする

### 3. 辞書の名前

Swift 標準の `Dictionary` 型と紛れるので、コードでは別の名前が要る。日本語も「辞書」のままでよいかを決めたい。`Catalog` は候補の 1 つ。

### 4. 注釈と感想の関係

vision.md では、人が重ねるものを「注釈」と呼んでいる。企画の段階では、特徴の値を直すこと、確認すること、感想を書くことを分けていた。

- 案 A: 人が足すものを全部「注釈」と呼び、特徴の修正・確認・感想はその種類とする
- 案 B: 「注釈」は感想のような文章だけを指し、特徴の修正と確認は別の語にする

### 5. 切り口とお題の関係

切り口がまだ決まっていないので、お題との関係も決まっていない。コードでの名前を決めるときは、`Prompt`（FoundationModels の型）と `Theme`（UI のテーマ）を避ける。
