# docs の置き方と設計の進め方

この repo には複数のプロダクトを置き、docs もプロダクトごとに分ける。設計は人間と議論して決め、決まったことを docs に残す。

## 置き方

| 置き場所 | 中身 |
| --- | --- |
| `docs/README.md` | この文書。repo 全体の docs の置き方と決め方 |
| `docs/<プロダクト名>/vision.md` | プロダクトの目的と前提。人間が決める |
| `docs/<プロダクト名>/glossary.md` | 用語と、コードでの名前 |
| `docs/<プロダクト名>/architecture.md` | 決まった構成。データモデルや処理の流れも、この文書の節として書く |
| `docs/<プロダクト名>/decisions/` | 決定の記録。1 つの決定を 1 ファイルにする |

設計の文書はこの形にそろえる。まだ無いファイルは、最初に必要になったときに作る。architecture.md には決まった構成を書き、実装と食い違っていることに気づいたら issue に挙げる。複数のプロダクトにまたがる決定が出てきたら、その置き場所はそのときに決める。

## 読むとき

issue を実装する前と、型名・データの形・外部サービスを足すときは、そのプロダクトの decisions/ と glossary.md を確かめ、決まった決定と名前に従う。状態が「置き換え済み」の決定は読まなくてよい。

docs に書いていない設計は、まだ決まっていないものとして扱う。当たったら、issue か会話で質問と推奨案を出し、決まるまでその部分の実装に入らない。

## 決め方

1. 論点を issue に挙げる。選択肢と、それぞれのトレードオフを添える
2. 人間と議論して決める
3. 決まったことを PR にする。マージした時点で決まったものとする

後から変えるとデータの移し替えや多くのファイルの書き換えが要る決定は、decisions/ に書く。用語の名前のように直せば済むものは glossary.md などを直し、理由は PR の説明に書く。

## decisions/ の書き方

ファイル名は `0001-短い名前.md` のように連番にする。中身は次の 4 つ。

- 状態: 採用 / 置き換え済み。PR では「採用」として書き、マージしなければ採用されない
- 背景: 何を決める必要があったか
- 選択肢: 検討した案と、それぞれのトレードオフ
- 決定: 選んだ案と理由

決定を覆すときは、元のファイルを消さずに状態を「置き換え済み」にし、新しいファイルへのリンクを付ける。食い違う記述が両方とも「採用」のまま残ると、エージェントがどちらに従うかが定まらないため。

## 名前のそろえ方

新しい用語は、議論で決めた時点で glossary.md に足す。コードの名前を変えるときは、glossary.md も同じ PR で直す。Swift のコードでは [API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/) に従う。
